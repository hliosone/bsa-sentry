BSA Sentry

Know Your Agent, enforced by your Ledger.

An AI agent gets a mandate held by your Ledger: our own Flex app is its wallet and policy engine, the EU Digital Identity Wallet supplies its Know Your Agent rights, and our x402 facilitator lets any shop sell to it in USDC on Arc. The agent acts on its own inside the mandate; the human decides only at its boundary.

Autonomous: in-policy payments to trusted merchants; presenting granted rights. Human on the Flex: new merchants, over the automatic limit or budget, rules, granting or changing rights, top-ups. Never: above the hard limit, no armed session, wrong chain or token (the Flex refuses); rights not granted or revoked (the facilitator refuses).

Ledger N3XT Hackathon @ OP3N 2026 · EPFL Blockchain Student Association · Arc testnet (chainId 5042002) · USDC via EIP-3009

1 · Our own Ledger app, the agent's wallet

A sideloaded Flex app holds 0xMAIN and 0xAGENT (never exported), the rules (automatic limit, hard limit, budget, payment count, trusted merchants) and the agent's rights. AUTO signs silently in 1 to 2 s, ASK shows Reject / Pay once, plus Trust merchant for an unknown merchant (60 s = deny), REFUSE cannot be overridden. It builds every digest itself.

2 · Know Your Agent, from the EU wallet

One EU Digital Identity Wallet presentation, verified by the EU Digital Identity Wallet reference verifier; we keep only "18 or older" and a jurisdiction. The Flex signs a Bind, our verifier attests, the Flex delegates chosen rights to its agent. Revocable. Demo uses a test PID; production uses a member state PID.

3 · Agentic commerce rails

Our x402 facilitator settles USDC on Arc and enforces the rights a merchant lists in extra.requires (age_over_18, jurisdiction_not:US). Merchants keep the standard x402 middleware; Shopify stores too. A remote MCP server with OAuth serves any MCP agent (tested with Claude) via one browser tab bridged to the Flex.

1System overview

Orange: one paid request. The agent and the server only request; the Flex decides and signs. No local daemon: one Chrome tab with the Flex plugged in. The server also serves the website and proxies the demo shops (/shops/*).

3Flows

Numbers in each diagram match the steps below it.

3a · Login with Ledger (SIGN_LOGIN)

  1. Connect. Chrome's WebHID prompt; GET_ADDRESS reads 0xMAIN (m/44'/60'/0'/0/0) and 0xAGENT (m/44'/60'/1'/0/0).
  2. Challenge. A one-time 32-byte nonce bound to the website origin, valid 5 minutes.
  3. Sign. The Flex shows the site, "Your main account", network and expiry. Hold: 0xMAIN signs the Login digest the Flex built itself.
  4. Verify. The nonce is burned on first use. The signer is recovered over a Login rebuilt with the server's own origin, so a Login made for a phishing site fails.
  5. Session. HMAC-signed cookie, HttpOnly, SameSite=Lax, 12 h. The account id is 0xMAIN.
  6. Bridge. The tab opens /relay with the cookie and reports its status.

3b · Setting the rules (SET_POLICY)

  1. Form. Auto-approve max, hard max, budget, max payments, up to 8 trusted merchants (address + 16-byte label). Defaults: cafe, wine shop, restaurant, presale. The bakery is left out on purpose.
  2. Send. 250-byte chunks: P1 00 first / 01 next, P2 80 more / 00 last, 1024 bytes max.
  3. Reassemble. Nothing is shown or stored before the last chunk.
  4. Review. Network, token, limits, budget, count, then each merchant's label and full address. The user holds "Approve rules".
  5. Store. Rules go to NVM, counters reset to zero. Reject: 6985 USER_REJECTED, nothing changes.
  6. Refresh. GET_STATE; the bridge forwards it to the server.

The Flex menu works without any host: remove a trusted merchant, reset the budget, or "Block agent" (erases rules and merchants, like CLEAR_POLICY).

3c · Arming the agent session

  1. On the Flex only. Settings, "Agent session" on. No APDU arms it (shipped build). It is saved on the device and stays on across app restarts until you turn it off there; blocking the agent turns it off too.
  2. Read back. sentry_status makes the relay ask the tab for a fresh GET_STATE.
  3. Report. The tab sends the session flag and the state blob.
  4. Tell the agent. Session, budget left, limits. Session off: every PAY is NO_SESSION.

3d · Connecting an agent (OAuth 2.1 + dynamic client registration)

  1. Add the URL. {PUBLIC_API_URL}/mcp as a remote MCP server. No token yet: 401 pointing to the resource metadata.
  2. Discovery. Protected-resource and authorization-server metadata: endpoints, S256, one scope, payments:request.
  3. Register (RFC 7591). https redirect URIs only (localhost excepted).
  4. Authorize. Client, exact redirect URI, response_type=code, PKCE S256 and resource are checked. Not logged in: Ledger login (3a), then back.
  5. Consent. "Allow agent to request payments from your Flex?", with a CSRF token bound to the account and the exact request.
  6. Code. 10 minutes, stored hashed. Deny returns access_denied.
  7. Token. Access 1 h, refresh 30 days. A replayed code revokes what it produced; refresh tokens rotate, and a reused one kills the family.
  8. Use. Each call gets a fresh MCP server bound to that account. The Agent page lists and revokes grants.

3e · A paid x402 request, end to end

  1. Tool call. x402_fetch {url}; the Bearer selects the account.
  2. Fetch. Anything but 402 comes back as free content.
  3. 402. PAYMENT-REQUIRED lists offers: scheme, network, asset, amount, payTo, timeout, optional extra.requires.
  4. Build. From the exact USDC offer on eip155:5042002: to, value, validAfter=0, validBefore at most 300 s ahead, random nonce, and a 24-byte hint from the merchant's description.
  5. Relay. sign_payment to the account's tab; 120 s without an answer is TIMEOUT.
  6. PAY. 176 bytes of raw fields plus the hint, over WebHID.
  7. Decide, in order:
    • REFUSE no rules, session off, other chain or token, zero, above hard max.
    • AUTO trusted address, at most auto max, within budget and count.
    • ASK otherwise, with the first reason: unknown merchant, above auto limit, budget exceeded, too many payments.
  8. Ask. Amount, label or "Unknown merchant", full address, "agent says: ... (unverified)", reason. Reject / Pay once / Trust merchant; Trust only if the unknown merchant is the only reason and the list has room. 60 s of silence counts as Reject (USER_REJECTED).
  9. Persist, then sign. On Trust, the new merchant (labelled with the hint) is saved first. Then spent, count and the last payment are written to NVM. Only then does 0xAGENT sign TransferWithAuthorization with from set to itself.
  10. Answer. v, r, s, or a reason. A refusal ends here: the agent is told "Refused by your Flex... Do not retry".
  11. Retry. Same GET with PAYMENT-SIGNATURE: authorization, signature, accepted offer.
  12. Verify. Offer equals the accepted one; to = payTo; value = amount; 6 s of validity left; the signature recovers to from (before any RPC); rights if required; nonce unused; balance.
  13. Settle. Facilitator key submits (maxFeePerGas 20 gwei or more). The receipt must hold exactly one matching USDC Transfer.
  14. Content with PAYMENT-RESPONSE (tx hash).
  15. Receipt. "Paid 3 USDC to 0x..., approved by the user's Flex" + explorer link; the dashboard updates live.

3f · Merchant requiring rights (x402 extension)

// apps/merchants/src/app.ts (condensed)
const server = new x402ResourceServer(
  new HTTPFacilitatorClient({ url: facilitatorUrl }),
).register('eip155:5042002', new ExactEvmScheme());

app.use(paymentMiddleware({
  'GET /wine': { accepts: {
    scheme: 'exact', price: '$4.5',
    network: 'eip155:5042002', payTo,
    extra: { requires: ['age_over_18'] },
  } },
}, server));

Merchant adds extra.requires:

  • age_over_18
  • jurisdiction_not:US,RU: no held jurisdiction in the list
  • jurisdiction_in:FR,DE: one held jurisdiction in the list

Payer adds paymentPayload.extensions.bsaAge: attestation, delegation and both signatures.

  1. Requirement. The server sees extra.requires and sets wantCredentials.
  2. Same decision. Rights never change the spending decision (3e).
  3. Read rights. After signing, the bridge reads GET_CREDENTIALS, no tap.
  4. Answer. Signature and the four credential blobs.
  5. Attach. They go into extensions.bsaAge of the signed retry.
  6. Check. After the payment checks, the chain below, fail closed. The chain id is the facilitator's, never the proof's.
  7. Verdict. On failure nothing settles and the agent learns which proof is missing. The Flex already counted the payment; the authorization expires unused within 5 minutes.
  8. Revoke. The website posts the credentials read from the Flex; only the 0xMAIN that signed the delegation can revoke it.
  9. Refused from now on. Its EIP-712 hash is stored; the facilitator answers DELEGATION_REVOKED.

The merchant sees the signed rights (e.g. age_over_18,jurisdiction:FR), 0xMAIN and 0xAGENT. Never a name or a birthdate.

3g · Agent identity grant (EUDI wallet to the Flex)

  1. Session. A 32-byte session id, bindable for 15 minutes.
  2. Request. DCQL to the EU verifier backend: one dc+sd-jwt PID (urn:eudi:pid:1) with birthdate, nationalities and issuing_country; direct_post.jwt, fresh nonce. The site shows the openid4vp:// QR.
  3. Scan with the wallet app (tested with Paradym).
  4. Present. The verifier checks issuer signature, key binding and nonce.
  5. Poll. The server reads the verifier's events, then the vp_token.
  6. Derive, then drop. Disclosed values only. 18+ from birthdate; jurisdiction from nationality, else issuing country. Kept: status and keccak256(transaction id). The birthdate never leaves one function.
  7. Bind. "Link your identity": verifier, session, "No personal data". Hold: 0xMAIN signs Bind.
  8. Check. Verified, unexpired, unbound, opened by the same account. The session is burned before anything is signed.
  9. Attest. Rights re-read from the verifier (never stored), signed by our verifier key: AgeAttestation for 0xMAIN, e.g. age_over_18,jurisdiction:FR, 30 days.
  10. Delegate. The user picks rights and an agent name. The Flex accepts only its own agent, shows name, full address, rights and expiry; hold: 0xMAIN signs AgentDelegation.
  11. Store. No tap. The Flex checks the delegation names its own 0xAGENT and re-signs the digest to compare (deterministic ECDSA: only its own 0xMAIN matches).

Changing one right: a new delegation from the same attestation (new nonce) is signed and stored, then the old one is revoked. Store first, so a failed revocation never leaves the user with nothing. Only attested rights can be granted.

Verified by the EU reference verifier. The demo uses a test PID from our own OpenID4VCI issuer (scripts/test-issuer.ts), since the EU test issuer requires hardware key attestation; production uses a member-state PID issuer.

3h · Top-up (TOP_UP)

  1. Balances read on chain: the Flex has no network.
  2. Request. 156 bytes: chain, token, value, validity, nonce. No recipient field.
  3. Review. Needs active rules on the same chain and token. The Flex fills in its own 0xAGENT; hold: 0xMAIN signs. Agent counters are untouched.
  4. Submit the signature to /topup.
  5. Check. The signer must be the logged-in 0xMAIN over a transfer to its agent; the balance must cover it.
  6. Settle. The server pays gas and requires one matching transfer in the receipt.
  7. Done. The tx hash goes to the dashboard.

3i · Key Ring backup and restore

  1. Read rules and credentials. No active rules: nothing to back up.
  2. Encode. A version byte, then the exact RESTORE payload.
  3. Switch to Ledger Sync on the Flex.
  4. Encrypt in the browser under the seed's trustchain (confirmation on the Flex the first time).
  5. Store the ciphertext.
  6. Restore from the Backup page, or from the agent: sentry_restore sends start_restore and the tab opens the restore page.
  7. Empty Flex only. Live rules or credentials stop it.
  8. Fetch, owner session only.
  9. Decrypt with Ledger Sync: only the same seed can.
  10. Review. One chunked RESTORE. The Flex re-checks the credentials, shows every rule and full address, the user holds. Counters start at zero.

5Security invariants and threat model

Invariants (each has tests)

  1. Rules change only after an on-device review and a hold.
  2. The Flex builds every digest from raw fields; no "sign this hash" command exists.
  3. Merchants match by address; labels are display only; "Pay once" never adds a merchant.
  4. Counters persist before a signature leaves the Flex; no silent signature outside the rules, none with the session off.
  5. 0xMAIN signs only Login, Bind, AgentDelegation and top-ups to its own 0xAGENT, after a review and a hold.
  6. The server can only request signatures; the facilitator re-verifies payments, rights and their link to the payer.
  7. OAuth tokens only allow requesting payments, and are revocable.
  8. No PID attribute is stored anywhere; the vault holds ciphertext only.

Trust anchors: the Flex for spending; our verifier key for rights (whoever holds it can attest anything); the EU verifier and the PID issuer for the identity data.
