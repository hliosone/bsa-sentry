EPFL Blockchain Student Association · Ledger N3XT Hackathon @ OP3N 2026

Your agent spends.Your Ledger decides.

BSA Sentry puts an AI agent's spending rules inside the secure element of a Ledger Flex. Claude pays for things on the web with x402 (USDC on Arc testnet), and a custom Flex app decides every single payment: not the agent, not our server, not a browser tab.

Ledger Flex · custom Rust appClaude via remote MCP + OAuthx402 · EIP-3009 USDCArc testnet · chainId 5042002EU Digital Identity WalletLedger Key Ring

In one minute. The user sets rules once on the website and approves them on the Flex: pay trusted merchants up to 5 USDC without asking, never pay more than 50, spend at most 20. Claude then shops on its own through our MCP connector. Every time a merchant answers 402 Payment Required, our server builds the payment and asks the Flex to sign it, through a Chrome tab that bridges the server (WebSocket) and the device (WebHID).

The Flex runs one pure function, decide(): inside the rules it signs with no tap; outside them it asks the human on its own screen (Reject / Pay once / Trust merchant, 60 s of silence means no); above the ceiling it refuses outright, even if the human taps. A web page that tricks Claude into a "mandatory 400 USDC deposit" never gets a signature.

On top: the agent can prove facts about its owner (18 or older, a jurisdiction) from an EU identity wallet without revealing who they are, the user can top up the agent from their main account with one hold, and everything on the Flex is backed up with Ledger Key Ring.

The pitch

What to say, and why each technology choice is there. If you only remember one sentence: the last word on the agent's money is in hardware.

"AI agents are starting to spend money for us. Today their limits live in software that a prompt injection can talk around. BSA Sentry puts them in the one place it can't: your Ledger."The 15-second opener (video script, 0:00)

The problem

Assistants like Claude can now browse, compare and buy. Giving them money means a hot key on a server, or a server-side spending policy. Both fail the same way: one prompt injection hidden in a web page, one server bug, one stolen token, and the limit is gone. The person is not in the loop at the moment it matters.

The idea

Move the spending policy into the device people already trust with their money. The hardware wallet stops being a confirm button and becomes a policy engine: it signs small, expected payments silently, asks the human only when a rule is broken, and refuses dangerous ones no matter what.

Why it matters for Ledger

Agents will hold spending power. BSA Sentry shows the Ledger can be where that power is governed, with no local daemon: one Chrome tab and a remote MCP connector, which is how consumers actually use assistants. It works with any MCP agent and any x402 merchant.

The boundary between the agent and the human

The hackathon brief asks for this explicitly. It is the whole product, and it is enforced by one pure function on the device (device-app/core/src/decide.rs, 34 tests).

Why these technologies

x402: payments that agents can doHTTP 402 Payment Required, revived by Coinbase: the merchant answers with a price, the client retries with a signed payment. No accounts, no checkout page, perfect for an agent. We use the official @x402/express 2.28 middleware.
EIP-3009: a payment is one signatureUSDC's TransferWithAuthorization lets the payer sign an off-chain authorization that anyone can submit. The agent key never needs gas or a network: the Flex signs, our facilitator settles.
Arc testnet: USDC is the native moneyCircle's L1, where gas is paid in USDC, so the agent only ever holds one asset. Fast finality (a payment settles in about 5 s). x402 2.28 supports it out of the box.
Remote MCP + OAuth: Claude as it is really usedclaude.ai talks to a server, not to the user's machine. Our MCP server is a standard remote connector with OAuth 2.1 (discovery, dynamic client registration, PKCE), so the user adds it in two clicks.
WebHID + Ledger DMK: no daemonLedger's Device Management Kit runs in Chrome. A website tab is the only bridge between the server and the device; nothing to install.

System overview

The Flex has no network: a website tab is the bridge. Everything else runs on our server. The server can request a signature; it can never make one.

Architecture decisions

No daemon: a browser tab is the bridgeThe DMK runs in Chrome over WebHID. The tab relays the server's requests to the Flex, one at a time. Everything else is online.
The server orchestrates, the Flex decidesThe agent API does all the x402 work. It can request a signature, never make one. Even a fully compromised server is still bound by the rules on the Flex.
The Flex protects the money, the facilitator protects the lawAmounts, merchants and budget are decided on the device. Merchant requirements (18+, jurisdiction) are checked by our facilitator. The facilitator has no spending rules at all.
The device builds every digestThe host sends raw fields; the Flex computes the EIP-712 hash itself. There is no "sign this hash" command, so the host cannot smuggle in anything else.
The account is 0xMAIN"Log in with Ledger": the Flex signs a Login message. OAuth for Claude sits on top of that session; consent requires it.
The Flex is the source of truthRules, counters, trusted merchants and the agent's credentials live in the Flex's NVM. The website only mirrors them. Key Ring keeps an encrypted copy.
Event-driven, never timersHidden tabs throttle timers to one per minute, so all device work starts from a WebSocket message. Proven: 100% of requests go through with the tab hidden.
Same architecture locally and onlineDocker Compose is the production topology; every URL comes from the environment; a cloudflared tunnel gives the public HTTPS URL claude.ai needs.

Rules and decide()

The policy lives in the Flex. It is set from the website, reviewed field by field on the device (every merchant label and its full address), and changes only after a hold.

The policy

Policy {
  active, chain_id: u64, token: [u8;20],
  auto_max: u64,   // paid without asking up to
  hard_max: u64,   // refused even if I confirm
  budget:   u64,   // total spending limit
  max_count: u16,  // payments before asking
  payees: [{ addr: [u8;20], label ≤16 B }; ≤8]
}                  // USDC base units, 6 decimals
Counters { spent: u64, count: u16 }   // NVM
Session  { armed: bool }              // RAM only

Demo values

Paid without asking up to5 USDC
Hard limit (never above)50 USDC
Budget20 USDC
Payments before asking10
Trusted merchantsCafe Sat, Corner Wines, Restaurant (the bakery is left out on purpose)

The agent session is started only from the Flex (gear icon → Agent session). It lives in RAM: quitting the app or unplugging turns it off.

The decision, in order

A pure function, no I/O, checked arithmetic. The first rule that matches wins.

1No active policyRefuse NO_POLICY
2The agent session is not started on the deviceRefuse NO_SESSION
3Chain or token differs from the policy'sRefuse WRONG_CHAIN_OR_TOKEN
4Amount is zeroRefuse INVALID_AMOUNT
5Amount above the hard limitRefuse OVER_HARD_MAX
6Payee address is trusted and amount ≤ auto limit and spent + amount ≤ budget and count < max countAuto: sign, no tap
7Otherwise, with the first reason of: UNKNOWN_PAYEE, OVER_AUTO_MAX, BUDGET_EXCEEDED, COUNT_EXCEEDEDAsk on the Flex

On Auto, or an approved ask

spent += value; count += 1; persist to NVM, then sign. A crash between the two can only under-spend, never sign twice past the budget.

The three choices

Reject → 6985 + USER_REJECTED. Pay once → sign, never adds the payee. Trust merchant → add the payee with the agent's hint as its label (after it was shown), then sign. Trust is offered only when the unknown merchant is the only problem and the list is not full. 60 s with no input → TIMEOUT.

Why the restaurant gets "Pay once" only

It is already trusted; it is 15 USDC over the auto limit. Trusting it again would change nothing, so the Flex does not offer it. The security rule beat the original demo script.

One payment, end to end

"Buy me a coffee at …/shops/cafe". Fifteen messages, about 5 seconds, one decision on the Flex. Blue arrows carry signing requests and answers; the device is the only place a signature is made.

  1. Claudecalls the MCP tool x402_fetch(url) with its per-user OAuth token.
  2. Serverthe agent API fetches the URL like any HTTP client.
  3. Shopanswers 402 with a PAYMENT-REQUIRED header: price, payTo, network, asset, and optionally extra.requires (e.g. ["age_over_18"]).
  4. Serverbuilds an EIP-3009 TransferWithAuthorization: from 0xAGENT, to payTo, value, validAfter 0, validBefore now + timeout, a random 32-byte nonce. It cannot sign it.
  5. Serversends sign_payment over the user's WebSocket, with the merchant's description as a hint, and wantCredentials if the offer has requirements. One request at a time per user; it waits at most 120 s.
  6. Tabsends PAY (176 bytes of raw fields + a ≤24-byte hint) to the Flex over WebHID.
  7. Flexcomputes the EIP-712 digest itself from the raw fields, runs decide(), persists the counters, and signs with 0xAGENT, or asks the human, or refuses.
  8. Flexreturns v‖r‖s, or 6985 + a reason byte.
  9. Tabanswers the server; if credentials were wanted it attaches the ones it read from the Flex (kept in memory only).
  10. Serverretries the request with PAYMENT-SIGNATURE (credentials go in paymentPayload.extensions.bsaAge).
  11. Shopasks our facilitator to verify, then settle. The facilitator recomputes the digest, checks ecrecover == from, amount and payee, time window, nonce unused, balance, and the identity chain if required.
  12. Arcthe facilitator submits transferWithAuthorization (maxFeePerGas ≥ 20 gwei, gas in USDC).
  13. Arcreceipt: only the USDC contract's Transfer log counts (Arc also emits an 18-decimal mirror log).
  14. Shopserves the content with a PAYMENT-RESPONSE receipt.
  15. Claudegets the content and {decision, amount, payee, txHash}. The dashboard shows it live (SSE) with an explorer link.

What the hint is, and is not. The agent's description of the merchant ("Bakery - croissant") is shown on the Flex in quotes with "unverified". Matching is always on the address, which is shown in full. A lying agent can change the words on screen, never who gets paid.

Onboarding (once)

About three minutes on the website, with the Flex plugged in and the BSA Sentry app open. The left rail of the site tracks these steps.

  1. Useropens the site in Google Chrome and clicks Connect: the WebHID picker lists the Flex. Webreads both addresses with GET_ADDRESS (0x08).
  2. WebLog in with Ledger: POST /auth/challenge gives a nonce; FlexSIGN_LOGIN (0x0F) shows the website's origin, the user taps; Serververifies the signature → httpOnly session cookie. The account is 0xMAIN.
  3. WebRules: a form pre-filled with the demo values and merchants, every device limit checked first. FlexSET_POLICY (0x0A, chunked) shows every field: each merchant's label and full address, the amounts, the token, the chain. Hold to approve. Counters reset.
  4. FlexStart the agent: gear icon → Agent session. Only the device can arm it; it lives in RAM.
  5. ClaudeConnect Claude: in claude.ai (Chrome) → Settings → Connectors → Add custom connector → <PUBLIC_URL>/mcp. Claude discovers the OAuth metadata, registers itself (DCR), and opens /oauth/authorize, which requires the Ledger session and shows the consent "Allow Claude to request payments from your Flex". PKCE S256; tokens stored hashed. The grant appears on the Claude tab, with a Revoke button.
  6. WebFund the agent: top up from the main account (see below), or the Circle faucet for testnet USDC.
  7. WebOptional: Agent identity (18+, jurisdiction) and Backup (Key Ring).

Keep the tab open. It is the bridge. A hidden tab or minimised window works (proven 100%); a sleeping laptop does not. If Claude says "open the BSA Sentry tab", reload it: it reconnects to the Flex without a click.

Top-up: main account → agent

The user's own USDC sits on 0xMAIN; Claude can only spend what is on 0xAGENT. Topping up is one hold on the Flex. Added in Phase C at the user's request, with invariant 5 updated on purpose.

  1. WebDashboard → Agent wallet → amount → Top up from main account. The balances shown come from GET /topup/wallets, read on Arc (the Flex has no network).
  2. Websends TOP_UP (0x14): 156 bytes, chainId · token · value · validAfter · validBefore · nonce. There is no recipient field: the device fills in its own 0xAGENT. A test proves a payload with 20 extra bytes is refused.
  3. Flexrequires active rules on the same chain and token, shows "Top up your agent": amount, from 0xMAIN, to 0xAGENT, network. Hold to sign with 0xMAIN. The agent's spending counters are untouched.
  4. ServerPOST /topup: recovers the signer and checks it is the logged-in 0xMAIN, that the transfer goes to this account's agent, and that the balance is there, before spending any gas. Then submits transferWithAuthorization (the server pays the gas) and confirms the transfer in the receipt.
  5. Web"Topped up 5 USDC" with an explorer link; both balances refresh.

Agent identity: facts, not identity

Some merchants must know something about the buyer: a wine shop needs an adult, a token presale must not sell to US persons. BSA Sentry lets the agent prove exactly that, from the user's EU Digital Identity Wallet, without the merchant, our server or the agent ever learning a name or a birthdate.

The rights

age_over_18: computed from the PID's birthdate, which is used for one comparison and dropped.

jurisdiction:CH: the country that issued the person's EU identity credential.

What merchants can require

age_over_18 · jurisdiction_not:US,RU · jurisdiction_in:FR,DE, in the x402 offer's extra.requires. Corner Wines requires age_over_18; the Token Presale requires jurisdiction_not:US.

Where they live

On the Flex. The user chooses which rights to grant; the Flex signs the delegation and stores it. Every rights bundle expires after 30 days and can be revoked at any time.

The payment

The EIP-3009 authorization, with attestation + delegation and both signatures in extensions.bsaAge. The facilitator walks the chain back to our issuer.

What the facilitator checks, in order

It trusts neither our server nor the merchant. Each failure has its own reason, which Claude relays to the user with the next step ("add it on the BSA Sentry website, Agent identity").

  1. The proof is present and well-formed (AGE_PROOF_REQUIRED, AGE_PROOF_INVALID). The chain id comes from the facilitator, never from the proof.
  2. The delegation's signature recovers to an address M, the owner (DELEGATION_INVALID_SIGNATURE).
  3. delegation.agent == authorization.from: the rights belong to this payer (DELEGATION_WRONG_AGENT).
  4. The delegation has not expired and has not been revoked (DELEGATION_EXPIRED, DELEGATION_REVOKED).
  5. The delegated rights meet the merchant's requirements (DELEGATION_MISSING_CLAIM; logic in satisfies(), packages/types/src/identity.ts).
  6. delegation.attestation is the EIP-712 hash of the attestation presented (ATTESTATION_HASH_MISMATCH).
  7. The attestation is signed by our issuer, its subject is M, and it has not expired (ATTESTATION_WRONG_ISSUER, SUBJECT_MISMATCH, ATTESTATION_EXPIRED).
  8. Every delegated right is one the attestation states: a delegation cannot inflate the rights (ATTESTATION_WRONG_CLAIM).

Where the jurisdiction comes from

The wallet is asked for the birthdate only: it is the one claim every PID answers (the Procivis test PID answered "credential missing" to a request for nationalities and to claim_sets). The country is then read, in order, from: a disclosed field if the deployment configures one (EUDIW_COUNTRY_CLAIM); an issuer-signed issuing_country visible in the payload; or the country (C=) of the issuer's certificate in the SD-JWT header (x5c), whose chain the EU verifier has just checked.

Revocation

  1. WebAgent identity → Revoke these rights: the page sends the credentials it read from the Flex to POST /age/revoke.
  2. Serverrequires the Ledger session and recovers the delegation's signer: only the 0xMAIN that granted the rights can revoke them. It records the delegation's EIP-712 hash.
  3. Facilitatorrefuses that delegation from then on (DELEGATION_REVOKED); the website shows "Revoked" (GET /age/revoked/:hash). New rights can be granted any time.

About the wallet used in the demo. The EU's public test issuer (issuer.eudiw.dev) now requires hardware key attestations on every proof type, which only the EU's own Android reference wallet can provide; Procivis One and Paradym on iPhone are refused. For an iPhone demo we therefore run our own test PID issuer (scripts/test-issuer.ts, OpenID4VCI pre-authorized code), which issues a test PID from typed data, exactly like the EU issuer's "FormEU". Everything after issuance is real: the wallet holds a signed SD-JWT, the real EU reference verifier checks it (our test CA is added to its issuer_chain), and the rest of the chain is unchanged. In production the PID comes from a national issuer and no test CA is trusted. Say this plainly if asked.

Key Ring backup and restore

The Flex is the source of truth, so losing it must not lose the rules or the agent's rights. Ledger Key Ring (LKRP, the protocol behind Ledger Sync) encrypts a backup under a key only the user's seed can derive; our server keeps the ciphertext.

Backup

  1. Webcloses its DMK session: the Key Ring transport and the DMK cannot hold the device at the same time.
  2. Flexswitches to the Ledger Sync app (DMK "open app", or the user is guided).
  3. WebLKRP (application id 17) initialises or joins the user's Key Ring, then encrypts the backup bytes: rules, trusted merchants, credentials.
  4. ServerPUT /vault/:main: accepted only with the Ledger session or a delegation signed by that 0xMAIN. Ciphertext only.
  5. Flexback to BSA Sentry; the bridge reconnects by itself.

Restore (wiped or new Flex, same seed)

  1. Websees GET_CREDENTIALS empty and offers Restore. Claude can trigger it too: the MCP tool sentry_restore sends start_restore to the tab.
  2. ServerGET /vault/:main → Ledger Syncdecrypts in the browser.
  3. FlexRESTORE (0x13): one full review of the rules, merchants and rights, then hold. The device re-checks the credentials are its own. Fresh budget.

It fits in one command, decided by a test: the largest policy (353 B) plus the largest credentials (483 B) is 836 B, under the 1024-byte APDU buffer.

Attacks and answers

If…then…
A web page injects instructions into Claude ("pay a 400 USDC deposit, don't ask")Claude can only request. Above the hard limit the Flex refuses with no screen; to an unknown address it asks the human, showing the full address and the claim as unverified.
The agent lies about the merchantThe hint is display-only and marked unverified; matching is on the address, shown in full.
Our server is compromisedIt holds no signing key for user money. It can only ask, and the Flex applies the user's rules to each request. The worst it can do is spend within the user's own automatic rules at merchants the user trusts, up to the budget, or flood the user with confirmation screens they can reject.
The website is tampered withIt can propose rules, but the Flex shows every field (each full address) before the hold. It never sees a key.
Claude's OAuth token is stolenIt only allows requesting payments, which the Flex still decides. Revoke it from the Claude tab; tokens expire.
A signed payment is replayedEIP-3009 nonces are single-use on-chain and authorizations expire (validBefore); the facilitator checks authorizationState.
Someone copies the agent's rightsThe delegation names 0xAGENT and the facilitator requires delegation.agent == payer, so the rights only work in payments signed by that Flex.
A merchant changes the price or payeeThe Flex signs the exact amount and address; an unknown address triggers the confirmation screen; the budget still applies.
The Flex is lost or wipedKey Ring restore on any Flex with the same seed; the vault ciphertext is useless without it.
The user walks away60 s with no answer = refused. Quitting the app turns the agent off.

Assumed limits

  • One Chrome tab must stay open next to the Flex; a sleeping laptop stops payments (documented, and the right failure mode).
  • Testnet only (Arc testnet USDC). Quick tunnels change URL on restart, which means re-adding the Claude connector.
  • Identity requirements are checked by our facilitator; a merchant relying on them trusts it. Revocations live on our server.
  • A merchant trusted through "Trust merchant" gets the agent's hint as its label, clipped to 16 bytes. Labels are display-only by design.
  • The live EU wallet step uses the EU's public reference verifier and, on iPhone, our test PID issuer (see Agent identity).

Ledger DX feedback, in one minute

A required deliverable (docs/DX_NOTES.md, 20+ entries). The five changes we would ask Ledger for first:

  1. An N-choice NBGL screen with a built-in timeout. Deny-by-default is the agent-approval primitive; today it costs ~130 lines of unsafe C-layout code, and the layout ticker pauses while the screen is touched (our 60 s timeout measured 155 s until we counted raw ticks).
  2. NBGL draws overflowing text underneath the buttons. It hid the "(unverified)" caveat on our confirmation screen. On a confirmation screen that is a security bug: clip, scroll or fail loudly.
  3. The SDK bakes derivation paths in at build time and ships an app that crashes on first derivation after a manifest change, instead of rebuilding or failing the build.
  4. Speculos swipes are undocumented (x2/y2 on /finger); every touch-device CI needs them.
  5. No pattern for remote agents. Hosted assistants talk to a server, not to the user's machine; the approval step has to live in a browser next to the device. That is most of what we built.

What worked well: Speculos (device tests with the Flex unplugged), on-device EIP-712 matching viem and the chain on the first try, silent signing, the DMK in Vite with no polyfills.

Judges' questions

Short answers first; the detail is there if they push.

Why not just a software wallet with spending limits?

Software limits live in the same place the attack happens: the agent's process, the server, or a browser a prompt injection can steer. Here the limits are enforced by the secure element, the device builds the digest itself, and the human-in-the-loop screen is on hardware the attacker does not control. The agent can only request; the server can only relay.

What if your server is compromised?

It holds no key that can move user money. It can only send signing requests, and the Flex applies the user's rules to each one: at worst it spends within the automatic rules at merchants the user already trusts, up to the budget. Identity cannot be forged either: the facilitator recovers every signature back to the user's Flex and our issuer.

What if the agent lies about who it is paying?

The agent's description is shown as a quote with "unverified". The Flex matches on the 20-byte address and shows it in full. Lying changes the words on screen, never the recipient.

What exactly does the Flex show?

Home: the agent's name, budget left, last payment, network and session. On a confirmation: "Pay X USDC on Arc?", the reason (unknown merchant, above auto limit, budget or count), the full address, the agent's claim marked unverified, and Reject / Pay once / Trust merchant, with a 60 s timeout. Every review (rules, delegation, top-up, restore) shows every field, and every screen names the token and chain.

What is x402?

An open standard (from Coinbase) that revives HTTP 402 Payment Required: the server answers with a machine-readable price, the client retries with a signed payment, a facilitator verifies and settles it on-chain. No accounts or checkout, which is why it fits agents. We use the official middleware and run our own facilitator.

Why Arc?

Circle's chain where USDC is the native gas token, so the agent holds exactly one asset and never needs a second token for fees. Payments settle in seconds, USDC supports EIP-3009, and x402 2.28 supports Arc testnet natively. The code is chain-agnostic (a CHAIN setting); Base Sepolia was proven as a fallback during feasibility.

Why not enforce the rules in a smart contract?

A contract wallet costs gas, lives on one chain, and still needs someone to approve exceptions. On the Flex the rules travel with the user's key, cost nothing, and the exception screen is in hardware in the user's hand.

Is the 18+ / jurisdiction proof private?

The wallet is asked for the birthdate only. "18 or older" is computed in memory and the birthdate is dropped; nothing personal is stored or logged. The merchant receives signed rights strings ("age_over_18", "jurisdiction:CH") bound to this agent, never a name, a date or a document number. Rights expire after 30 days and can be revoked.

Which EU wallet did you use, and is the PID real?

We verified the flow live with a real Procivis One wallet and the EU's public reference verifier (and bought wine with it on Arc). The EU's public test issuer now requires hardware key attestations that only the EU's own Android reference wallet provides, so iPhone wallets cannot get a test PID from it. For the iPhone demo, a small test PID issuer of ours issues a test credential from typed data, like the EU issuer's "FormEU", and the real EU verifier then checks it, with our test CA added to its issuer_chain. It is test data on a test network; in production the PID comes from a national issuer.

What if the laptop sleeps, or the tab is closed?

Payments stop: Claude is told "open the BSA Sentry tab". Nothing is signed without the device, which is the safe failure. Hidden tabs and minimised windows work; the bridge is event-driven precisely so browsers cannot throttle it.

What if the user loses the Flex?

Ledger Key Ring: the rules, trusted merchants and the agent's rights are backed up encrypted under the seed. A new Flex with the same seed restores them with one review. The vault on our server only ever holds ciphertext.

Does this only work with Claude?

No. Any MCP client that supports remote servers with OAuth can use the connector, and any x402 merchant can be paid. The device app and the signer kit know nothing about Claude.

What did you build in the hackathon versus before?

Before (disclosed in docs/PREEXISTING.md): Ledger's Rust app boilerplate, our own feasibility tests from 10–11 October on the same Flex, and the team's EU verifier test page. Everything else was built during the hackathon, test-first, and every reused piece was re-introduced under tests (the feasibility app's "sign with no policy" command was removed).

Glossary

x402
HTTP 402 Payment Required as a payment protocol: a priced 402 answer, a retry with a signed payment, a facilitator that verifies and settles.
Facilitator
The x402 service that verifies a signed payment and submits it on-chain. Ours also checks identity requirements.
EIP-3009
USDC's TransferWithAuthorization: the payer signs an off-chain authorization (amount, payee, validity window, nonce) that anyone can submit.
EIP-712
The standard for signing typed, structured data (a domain + a struct), so a device can show and hash exactly what is signed.
MCP
Model Context Protocol: how an AI assistant calls external tools. Our remote MCP server exposes x402_fetch, sentry_status, sentry_restore.
OAuth 2.1 / DCR / PKCE
How claude.ai gets a per-user token for our MCP server: dynamic client registration (DCR), an authorization code protected by PKCE, consent behind "Log in with Ledger".
DMK
Ledger's Device Management Kit, the TypeScript SDK to talk to Ledger devices; we use it in Chrome over WebHID.
WebHID
The browser API that lets a web page talk to a USB HID device such as a Ledger, in Chrome.
APDU
The command/response format between a host and a smart-card-like device; our app defines 12 commands under CLA E0.
NBGL
Ledger's UI library for touchscreen devices (Flex, Stax): reviews, choices, home screens.
NVM
The device's non-volatile memory, where the app keeps the rules, counters, merchants and credentials. Wiped on app reinstall.
Speculos
Ledger's device emulator. We run the Flex model headless and drive taps and APDUs over its REST API.
Key Ring (LKRP)
Ledger Key Ring Protocol, behind Ledger Sync: encryption keys derived from the seed, shared between a user's devices. We use it to encrypt backups.
Arc
Circle's L1 blockchain where USDC is the gas token. We use Arc testnet (chainId 5042002).
EUDI Wallet
The European Digital Identity Wallet: an app holding identity credentials issued by EU states (Procivis One is one implementation).
PID
Person Identification Data: the core EU identity credential (name, birthdate, nationality…), issued by a national PID provider.
SD-JWT VC
Selective-Disclosure JWT Verifiable Credential: a signed credential where each attribute can be revealed separately (we reveal only the birthdate).
OpenID4VP
OpenID for Verifiable Presentations: the protocol a verifier uses to request, and a wallet to present, credentials (here via a QR code).
OpenID4VCI
OpenID for Verifiable Credential Issuance: how a wallet receives a credential from an issuer (used by our test PID issuer).
DCQL
Digital Credentials Query Language: how the OpenID4VP request says which credential and which claims it wants.
issuer_chain
A per-request list of extra trusted issuer CAs that the EU reference verifier accepts.
0xMAIN / 0xAGENT
The user's identity key and the agent's spending key, both derived in the Flex from one seed.
Agent session
A switch on the Flex (RAM only) that must be on for any agent payment; only the device can turn it on.
Bind / AgeAttestation / AgentDelegation
The identity chain: the Flex binds a verification to 0xMAIN, our issuer attests the rights, the Flex delegates them to 0xAGENT.
